# Расчётное ядро Обнинск 2040

Рабочая библиотека TypeScript для браузера и Node.js. Она загружает район, применяет проекты и временные закрытия, считает пешеходную доступность, восстанавливает маршруты, сравнивает сценарии и подбирает недоминируемые варианты под бюджет. Версия ядра — `0.1.0`, контракт данных — `1.0.0`.

## Запуск

Нужны Node.js 22+ и pnpm. Версии инструментов зафиксированы lock-файлом. Все вычисления выполняются локально, без внешних API.

```powershell
pnpm install --frozen-lockfile
pnpm verify
pnpm demo
pnpm bench
```

`verify` собирает библиотеку, проверяет TypeScript в строгом режиме и запускает интеграционные и алгоритмические тесты. `demo` показывает показатели, маршрут и результаты точного подбора. `bench` запускает тест производительности на исходном районе и увеличенных независимых копиях. Копии служат только нагрузочным примером и не описывают связный реальный город.

Сборка создаёт:

- `dist/engine.js` — автономный ESM-модуль для браузера/Node.js;
- `dist/engine.worker.js` — автономный модуль Web Worker;
- карты исходников и декларации TypeScript.

JSON Schema проверяется Ajv draft 2020-12. Валидаторы генерируются на этапе сборки, затем включаются в ESM вместе с необходимыми вспомогательными функциями. На сайте нет компиляции схем через `eval` / `new Function` и нет загрузки Ajv из CDN. Этот подход описан в [документации Ajv по автономным валидаторам](https://ajv.js.org/standalone).

## Основной API

Пример для Node.js из каталога `examples`:

```js
import { readFile } from 'node:fs/promises';
import { createPlanningEngine } from '../dist/engine.js';

const engine = await createPlanningEngine(
  await readFile(new URL('../data/district.json', import.meta.url), 'utf8')
);

const scenario = {
  projectIds: engine.resolveProjects(['p_park_paving', 'p_kerbs']),
  budgetRub: 8_000_000,
  operationalOverrides: []
};

const result = engine.evaluate(scenario, ['walk', 'step_free']);
const route = engine.route(scenario, 'step_free', 'building_b00_sw', 'park');
const loads = engine.edgeLoads(scenario, 'step_free', 'park');
const map = engine.mapSnapshot(scenario, 'step_free', 'park'); // без маршрутов фигур
const animatedMap = engine.mapSnapshot(scenario, 'step_free', 'park', ['building_b00_sw']);
const colors = engine.networkAccess(scenario, 'step_free', 'park');
const saved = engine.exportScenario(scenario);
const restored = engine.importScenario(JSON.stringify(saved));
```

Фабрика принимает JSON-строку или разобранный объект. Она копирует и проверяет входные данные; изменения исходного объекта после загрузки не меняют ядро. Начальная SHA-256 требует Web Crypto: в браузере использовать HTTPS или localhost. Район, профили и результаты `evaluate` неизменяемы на уровне выполнения. Возвращённые маршруты и экспортные файлы являются отдельными объектами.

`evaluate()` без аргументов считает исходное состояние для всех профилей. Существующие сценарии из `district.json` тоже принимаются напрямую. Пустой сценарий может иметь любой неотрицательный капитальный бюджет; на маршруты величина бюджета не влияет.

| Метод | Результат |
|---|---|
| `getDataset()` | Проверенный неизменяемый исходный район |
| `getMetrics()`, `getProfiles()` | Копии настроек для интерфейса |
| `resolveProjects(ids)` | Зависимости и выбранные проекты в допустимом порядке |
| `materialize(scenario)` | Неизменяемый снимок изменённого района, расходы и нормализованный сценарий |
| `evaluate(scenario, profileIds?)` | Метрики по домам, агрегаты, сравнение с исходным состоянием, изменения для карты |
| `route(scenario, profileId, buildingId, metricId)` | Самый быстрый путь от дома до объекта выбранной метрики |
| `networkAccess(scenario, profileId, metricId)` | Время и попадание в порог для каждого узла сети |
| `optimize(input, control?)` | Точный выбор недоминируемых сценариев среди заданных кандидатов |
| `exportScenario`, `importScenario` | Сохранение/загрузка сценария с привязкой к содержимому данных |
| `cacheStats()`, `clearCache()` | Статистика и очистка кэша |

`resolveProjects` явно добавляет необходимые проекты, которые тоже нужно оплатить. `evaluate` сам не добавляет незаметно отсутствующие зависимости: неверный выбор отклоняется.

## Что получает интерфейс

`ScenarioEvaluation` содержит идентификатор, версию и отпечаток набора, нормализованный сценарий, расходы, `profiles`, `changesFromBaseline` и `districtChanges`.

Для каждого профиля доступны пять исходных показателей и настроенные дополнительные метрики. Для каждой метрики возвращаются население расчётной группы, число достигших объектов, число недостигших, охват по временному порогу и среднее время среди достигших. По каждому дому есть время, достижимость, попадание в порог и число оцениваемых жителей.

`districtChanges` содержит только изменённые записи узлов, рёбер, объектов притяжения и участков. Это **полные изменения относительно исходного района**, а не относительно предыдущего состояния экрана. Для переключения сценария нужно восстановить ранее изменённые записи из базы и наложить новый набор изменений. Это предотвращает «залипание» сквера или перенесённой остановки после сброса.

Идентификаторы объектов сохраняются, поэтому карту можно обновлять по ID. Проекты не меняют геометрию зданий и улиц; новые пути и места остановок уже подготовлены в данных. Свободное рисование новых геометрий требует отдельного геометрического редактора и проверки барьеров.

Маршрут содержит `nodeIds`, `edgeIds`, локальную полилинию, GeoJSON, длину, общее время, время ходьбы и ожидания. Он оптимален **по времени**, не обязательно по метрам. Геометрия рёбер разворачивается при прохождении в обратную сторону.

При недостижимости возвращаются `reachable: false`, пустые массивы и `null` вместо времени/длины. При достижимом маршруте из нуля рёбер геометрия содержит одну точку, а GeoJSON-линия равна `null`; такую точку интерфейс может показать маркером. Неизвестный ID — ошибка, а не недостижимость.

## Новые показатели и профили

Алгоритм не привязан к пяти названиям метрик. При загрузке можно задать свой реестр:

```js
const engine = await createPlanningEngine(dataset, {
  metrics: [
    { id: 'children_school', destinationKinds: ['school'],
      thresholdSeconds: 600, populationGroup: 'under18' },
    { id: 'daily_services', destinationKinds: ['grocery', 'community'],
      thresholdSeconds: 900, populationGroup: 'all' }
  ],
  additionalProfiles: [
    { ...dataset.profiles[0], id: 'custom_slow', speedMps: 0.6 }
  ],
  cacheMaxEntries: 24,
  cacheMaxBytes: 64 * 1024 * 1024
});
```

Параметр `metrics` заменяет реестр целиком. Чтобы дополнить исходные метрики, использовать `defaultMetrics(dataset)` и добавить новые определения. Реестр не меняется после создания экземпляра: другой набор настроек — другой экземпляр, что исключает использование устаревших результатов кэша.

Группы населения: `all`, `under18`, `age18to64`, `age65plus`, `mobilityNeeds`. Последняя пересекается с возрастными и не должна прибавляться к ним. При нулевой численности группы процент и среднее равны `null`. Данные по всем профилям относятся к одним и тем же жителям; их нельзя складывать.

Определения с одинаковым набором типов объектов используют одно дерево маршрутов даже при разных порогах и группах населения. Добавление порога не требует дополнительного запуска Дейкстры. Новые типы объектов и поверхностей за пределами версии схемы требуют явного изменения контракта данных; новые типы операций также требуют реализации и тестов.

## Сценарии и проверки

Схема проверяется на входе. При загрузке дополнительно проверяются уникальность ID, ссылки, геометрические длины и площади, население, совместимость остановок, циклы зависимостей и необъявленные конфликтующие записи проектов. Сохранённые сценарии проверяются при загрузке; итоговое состояние проверяется при каждом применении.

Полная проверка полигонов, пересечений, проезжих частей и ограждений остаётся в `tools/validate_dataset.py`. Это проверка исходной географии на этапе подготовки данных. Runtime не повторяет дорогие пространственные проверки при каждом расчёте: сценарий может изменять только заранее подготовленные связи и поля, а не произвольные координаты. Произвольный внешний район должен сначала пройти полную проверку подготовки данных.

`operationalOverrides` принимает только `set_edge_active`. Разрешены временные закрытия и повторное открытие уже существующего либо построенного выбранными проектами пути. Нельзя включить ещё не построенный переход или бесплатно изменить поверхность, уклон, парк, остановку. Допускается изоляция дома: она ухудшает показатели, а не приводит к ошибке загрузки.

Капитальный бюджет и ежегодные расходы различаются. Бюджет ограничивает только `capexRub`, ежегодные расходы возвращаются отдельно. Повторы проектов, нарушенный порядок зависимостей, взаимоисключения, превышенный бюджет и неизвестные ссылки отклоняются до использования кэшированных маршрутов.

Ошибки имеют стабильный `EngineError.code`: `INVALID_DATASET`, `INVALID_INPUT`, `UNKNOWN_ID`, `INVALID_SCENARIO`, `BUDGET_EXCEEDED`, `PROJECT_CONFLICT`, `DEPENDENCY_ERROR`, `INVALID_STATE`, `SEARCH_LIMIT`, `CANCELLED`, `DATASET_MISMATCH`, `WORKER_DISPOSED`. Интерфейс должен ориентироваться на код, а не разбирать английский текст сообщения.

## Подбор проектов

```js
const controller = new AbortController();
const best = await engine.optimize({
  profileId: 'walk', metricId: 'park', budgetRub: 8_000_000,
  topK: 3, maxCandidates: 16, maxFrontierSize: 4096
}, {
  signal: controller.signal,
  onProgress: ({processedSubsets, totalSubsets}) => {
    console.log(processedSubsets, totalSubsets);
  }
});
```

Опционально задаются `candidateProjectIds` и `requiredProjectIds`. Их зависимости добавляются в возвращённый каталог и включаются в стоимость. Подбор не снимает выбранные обязательные проекты. Несовместимые обязательные проекты или недостаточный бюджет вызывают ошибку.

Сначала исключаются комбинации с нарушением бюджета, зависимостей и несовместимостей. Для остальных считается выбранная метрика и профиль. Остальные показатели можно получить обычным `evaluate` для понравившихся вариантов.

Из результатов удаляются доминируемые варианты: если другой проект даёт не меньший охват и достижимость, не большее суммарное время и расходы и хотя бы по одному признаку лучше, более слабый вариант не предлагается. Полностью одинаковые результаты представлены одним детерминированным набором ID. Это граница Парето. Её полнота не означает, что каждый вариант равноценен пользователю.

Из этой границы выбирается `topK` по явному правилу:

1. Максимум жителей в заданном временном пороге.
2. Максимум жителей, которые вообще могут достигнуть объекта.
3. Минимум суммы `население × время` для достигших, округлённой до 6 знаков.
4. Минимум капитальных, затем ежегодных расходов.
5. При полном равенстве — лексикографический порядок ID.

Это одна определённая целевая функция; она не является универсальным индексом качества города. Польза для иных типов объектов и другие профили здесь не оптимизируются автоматически. Порядок критериев доступен в `rankingRule`.

Результат точен только среди возвращённых `candidateProjectIds`. Полный каталог из 12 проектов требует 4096 подмножеств. По умолчанию разрешено до 16 кандидатов после добавления зависимостей; явный верхний предел — 20. Размер сохраняемой границы по умолчанию ограничен 4096 вариантами, настраивается до 65536. При превышении лимита возвращается `SEARCH_LIMIT`, а не неполный результат с отметкой точности.

Перебор экспоненциальный. Рост числа узлов обрабатывается эффективным графовым ядром, но не делает полный перебор тысяч проектов возможным. Для больших каталогов нужно задавать небольшой пул кандидатов либо добавлять отдельный решатель/эвристику с собственным описанием гарантий.

Отмена кооперативная: проверяется между комбинациями, а управление передаётся циклу событий по умолчанию каждые 16 подмножеств. `yieldEvery` доступен в прямом API. Один большой запуск Дейкстры не прерывается посередине. Для мгновенного прекращения Worker можно завершить через `dispose`.

## Работа в Worker

Пример предполагает, что код находится во входном модуле в корне проекта, а сервер отдаёт `dist` и `data`; при интеграции с Vite путь нужно задать относительно реального входного файла:

```js
import { EngineWorkerClient } from './dist/engine.js';

const client = new EngineWorkerClient(
  new Worker(new URL('./dist/engine.worker.js', import.meta.url), { type: 'module' })
);
await client.init(await (await fetch('./data/district.json')).json());

const result = await client.evaluate({ projectIds: [], budgetRub: 8_000_000 }, ['walk']);
const controller = new AbortController();
const best = await client.optimize(
  { profileId: 'walk', metricId: 'park', budgetRub: 8_000_000 },
  { signal: controller.signal, onProgress: console.log }
);
// При удалении экрана или приложения:
client.dispose();
```

Клиент поддерживает расчёт, маршрут, `networkAccess`, оптимизацию и импорт/экспорт сценария. Запросы связываются по ID, поддерживают ошибки и отмену. При замене района старые задачи отменяются и не публикуют результат для новой базы. Ошибки callback прогресса завершают обещание и отменяют фоновую работу. Авария/закрытие Worker отклоняет ожидающие вызовы.

Для реактивного интерфейса отменять старый запрос через `AbortController`, когда пользователь меняет сценарий. Вызовы независимы: клиент не решает за приложение, какой из двух успешно рассчитанных сценариев пользователь хочет видеть.

## Производительность и расширение

Слои ядра:

- `validation.ts` — структурный контракт и семантические проверки;
- `scenario.ts` — зависимости, бюджет и применение операций с копированием изменяемых записей;
- `graph.ts` — индексация ID, типизированные массивы CSR, ограничения профиля, двоичная куча, Дейкстра;
- `metrics.ts` — реестр показателей, группы населения, агрегаты, сравнение и восстановление маршрута;
- `optimizer.ts` — точный перебор и граница Парето, без зависимости от интерфейса;
- `engine.ts` — высокоуровневый API, отпечаток данных и ограниченный LRU-кэш;
- `worker-runtime.ts`, `worker-client.ts` — протокол и жизненный цикл фоновых запросов.

Один поиск от множества целей стоит `O((V + E) log V)` по времени и `O(V + E)` по памяти. Он выполняется для уникальных наборов типов объектов, а не для каждого дома. ID переводятся в числовые индексы один раз; для профиля используются CSR и типизированные массивы. Структурно неизменённые геометрии общие для сценариев. Пустой сценарий использует исходный снимок напрямую.

Кэш ограничивается количеством записей и оценкой памяти. По умолчанию — 24 записи и примерно 32 МиБ; оценка учитывает типизированные массивы точно и объекты приблизительно, это не ограничение всей JS-кучи процесса. При большом районе/числе метрик нужно выбирать активный профиль и при необходимости увеличивать бюджет кэша. Превышающий бюджет результат рассчитывается, но не сохраняется в кэш.

Нагрузочный скрипт измеряет загрузку, первый расчёт трёх профилей, повторный расчёт и маршрут для 188, 4700 и 18800 узлов. Результаты зависят от машины и нагрузки. Гарантии времени для реального города не заявляются: отдельно остаются стоимость подготовки географии, число показателей, сериализация и визуализация.

## Сохранение и воспроизводимость

Сценарий содержит ID, версию и SHA-256 **канонического содержимого** района. Канонизация сортирует ключи объектов и не зависит от пробелов JSON, но сохраняет порядок массивов. Этот отпечаток отличается от файлового SHA-256 в `data/manifest.json`, который относится к точным байтам файла. Одинаковый формат и версия при другом содержимом не разрешают тихо загрузить старый сценарий.

В репозитории остаётся Python-эталон. Тесты сверяют все 18 комбинаций сохранённых сценариев/профилей, все маршруты жилых домов, направленный граф с независимым Беллманом—Фордом, демографические группы, недостижимость, изменения карты, кэш, импорт и отмену. Два результата оптимизации проверяются полным независимым перебором на Python, включая отсечение доминируемых вариантов. Worker проверяется в отдельном реальном потоке Node.js с адаптером браузерного `self`; это не тест отрисовки или браузерного интерфейса.

При изменении исходных данных сначала пересоздать их и эталонные отчёты, затем обновить контрольный пример оптимизатора:

```powershell
python tools/build_dataset.py
python tools/generate_engine_oracle.py
pnpm verify
```

Валидация runtime не заменяет городское моделирование. Расчёты сохраняют допущения исходного набора: условные жители и стоимости, постоянная скорость, фиксированное ожидание, открытые объекты, отсутствие распределения по вместимости и транспортной модели.
