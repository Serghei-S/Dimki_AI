# Нагрузка сети и оптимизация

## Реализовано

Основной режим — световая подсветка рёбер. Фигуры жителей выключены по умолчанию и включаются отдельно кнопкой «Жители» или через слои. Их количество не влияет на нагрузку.

Единица нагрузки — **условный проход жителя за модельный цикл**. Каждый житель идёт от лучшего входа своего дома к ближайшему достижимому объекту выбранной категории. Вес дома суммируется по всем рёбрам пути. Учитываются все дома, ограничения профиля, направления и текущий сценарий. Недостижимые жители не создают поток и учитываются отдельно. Прямое и обратное направления сохранены раздельно.

Это не одновременная плотность толпы и не поток в час. Для почасового прогноза нужны расписания, частоты поездок и калибровка спроса. Категории целей оцениваются отдельно; один человек не превращается в несколько независимых жителей.

Шкала неизменна между сценариями: зелёный до 250 проходов, жёлтый до 500, оранжевый до 750, красный от 750. При 1000+ цвет и толщина насыщаются; это визуальный диапазон, а не предел пропускной способности. Нулевые рёбра тонкие и приглушённые. Список трёх самых нагруженных участков открывает карточку с потоком, направлениями, длиной и шириной и приближает камеру.

| Изменение | Для чего |
|---|---|
| Агрегация по дереву кратчайших путей | Спрос переносится от входов домов к целям по убыванию расстояний, без построения геометрии маршрута каждого дома. После расчёта дерева: `O(B + V log V + E)` плюс число входов |
| Один `map_snapshot` в Worker | Отчёт, исходное состояние, нагрузка и необязательные маршруты фигур возвращаются согласованным ответом с повторным использованием анализа |
| Ленивые фигуры | В основном режиме не запрашиваются маршруты выборки и не создаются семь InstancedMesh жителей. Выключение освобождает их GPU-ресурсы |
| Подсветка одним InstancedMesh | Все допустимые отрезки сети — один draw call, процедурный световой ореол без полноэкранного bloom |
| Рендер по запросу | В простое нет постоянного requestAnimationFrame. Камера/данные/настройки возобновляют кадры, включённые жители используют непрерывный режим |
| Разделение обновлений геометрии | Смена категории или слоя фигур не пересоздаёт деревья, парки и здания |
| Интерфейс `PlanningService` | Будущий HTTP-адаптер может реализовать те же методы, что нынешний Worker |

Режим рендера, счётчик кадров, число draw calls и треугольников доступны как диагностические `data-*` атрибуты контейнера карты. При паузе и скрытой вкладке лишние кадры останавливаются.

Проверка реализации: 38 Node-тестов прошли, включая независимую сумму направленных маршрутов для всех сценариев/профилей/целей, недостижимые дома, отсутствие целей, демографические веса и интеграцию Worker. В браузере основной режим остановился после двух кадров; включение 360 фигур изменило 99 draw calls / 146828 треугольников на 106 / 210908. После выключения ресурсы вернулись к исходным, рендер остановился. Проверены карточка участка, смена профиля и перераспределение при добавлении сквера и сравнении «До/После».

## Замеры

Воспроизведение: `node examples/flow-benchmark.mjs` после сборки. Результат — `data/reports/flow-performance.json`. Node.js v24.19.0, текущий компьютер, семь последовательных прогретых повторов, медиана. Передача Worker/HTTP, React и GPU в измерение не входят.

| Узлы / рёбра | Дома | Первый снимок, мс | Прогретый снимок с агрегацией, мс | Явные маршруты всех домов + сумма, мс |
|---|---:|---:|---:|---:|
| 188 / 277 | 35 | 12,24 | 0,80 | 1,30 |
| 4700 / 6925 | 875 | 53,78 | 8,05 | 67,67 |
| 18800 / 27700 | 3500 | 127,12 | 27,14 | 624,20 |

Последняя строка даёт примерно 23-кратную разницу между этими способами подготовки потока. Это **не сравнение JavaScript и Python**. Нагрузочные наборы — независимые копии района, а не связный настоящий город. Не следует переносить эти числа на полную задержку интерфейса.

## Python-бэкенд: когда полезен

Рекомендация для текущего локального проекта — оставить интерактивные расчёты в Worker. Сервер добавлять для общих результатов, хранения, реальных GIS-данных и тяжёлых задач. Смена языка сама по себе не гарантирует ускорения; цена передачи, очереди и эксплуатации тоже входит в задержку. Нагрузка 3D-отрисовки останется на клиенте.

| Подход | Когда выбирать | Цена |
|---|---|---|
| TypeScript Worker | Локальный район, быстрые правки, работа без API | Ресурсы клиента, отдельный кэш каждого пользователя |
| Node API с текущим ядром | Серверный общий кэш и расчёты без второго алгоритма | Нужны очередь, ограниченный пул worker_threads и сервер |
| FastAPI + Python workers | GIS, научные модели, массовые и длительные расчёты | Отдельные процессы, перенос/проверка алгоритма и инфраструктура заданий |
| Rust/WASM или нативное ядро | Замеры подтвердили дорогое вычислительное ядро | Более сложная сборка и отладка; обязательны замеры передачи данных |

FastAPI различает конкурентное ожидание I/O и CPU-параллелизм: `async` не ускоряет тяжёлый вычислительный цикл. Для обычного CPython с GIL тяжёлые Python-циклы можно выносить в отдельные процессы; дополнительные потоки сами по себе не гарантируют ускорения. Сборки Python без GIL существуют, но требуют проверки зависимостей и измерений. Основания: [FastAPI](https://fastapi.tiangolo.com/async/), [ProcessPoolExecutor](https://docs.python.org/3/library/concurrent.futures.html#processpoolexecutor), [free-threaded Python](https://docs.python.org/3/howto/free-threading-python.html).

Для Python стоит проверить разреженную CSR-матрицу и [SciPy Dijkstra](https://docs.scipy.org/doc/scipy/reference/generated/scipy.sparse.csgraph.dijkstra.html), включая `min_only=True`. Для поиска к целям требуется обратить направления графа. При переносе сохранить исходные ID рёбер, односторонние связи, ожидания, ограничения профилей, выбор входа и правила равных маршрутов. Параллельные рёбра нельзя просто сложить при создании CSR. SciPy предупреждает, что выбор равноценных путей может зависеть от версии: одинаковые времена не гарантируют одинаковое распределение нагрузки.

## Реалистичный порядок следующих улучшений

1. **Профилирование целиком:** отдельно время вычислений, сериализации/передачи, обновления сцены и GPU; p50/p95, память и время первого результата на ноутбуке и телефоне.
2. **Большие сцены:** пространственные чанки, LOD зданий/окон/подписей, отсечение вне кадра, адаптация DPR и плотности фигур. Серверный Dijkstra не заменяет эти графические улучшения.
3. **Большие ответы:** стабильный порядок ID, типизированные массивы нагрузок, transferable buffers и изменения вместо повторного полного JSON. Передача буфера отсоединяет его у отправителя, поэтому нельзя передавать единственный экземпляр из общего кэша.
4. **Сервер при необходимости:** API версий наборов и сценариев, ключ кэша с SHA-256 данных, версией алгоритма, профилем, метрикой и допущениями спроса. PostgreSQL/PostGIS — при реальных GIS-данных и совместной работе; права личных сценариев отделить от общего базового кэша.
5. **Тяжёлые задания:** ограниченный пул процессов, очередь с ID задания, прогресс/SSE или опрос, отмена, лимиты времени и памяти. Не создавать процесс на каждое движение ползунка. Старые запросы не должны перезаписывать новые. Полный перебор проектов экспоненциален и на сервере.
6. **Сравнение перед миграцией:** Worker, Node API с текущим ядром и Python/SciPy на одинаковых входах, холодном/тёплом кэше и равных ресурсах. Нынешние регрессии, направления и нагрузки должны совпасть до переключения интерфейса.

Предлагаемые ориентиры, пока не гарантии: интерактивный ответ до 100–150 мс на целевом устройстве; задачи, регулярно занимающие более 0,5–1 секунды, — кандидаты на фоновое выполнение. Если узкое место — GPU, сначала LOD/DPR, затем обсуждение серверных вычислений.
