# Модель данных района Сосновый

Версия схемы и данных — `1.0.0`. Канонический файл — `data/district.json`. Формат рассчитан на перенос расчётов в TypeScript без зависимости от Python и на расширение числа кварталов и проектов.

## Происхождение и система координат

Все значения синтетические. Генератор не использует персональные данные, кадастр, OpenStreetMap, цены подрядчиков и муниципальные API. Он создаёт небольшой район с согласованной геометрией, а не восстанавливает реальную территорию.

Локальная система `LOCAL_METERS`: X направлен на восток, Y на север. Основная сетка района — 1280 × 960 м; рамка `boundsM` включает дороги на внешних границах. Формат точки — `[x, y]`; формат рамки — `[xmin, ymin, xmax, ymax]`. Длины, площади, пересечения и маршруты вычисляются только в этой системе. Полигоны замкнуты, внешнее кольцо направлено против часовой стрелки; отверстий и разновысотных пересечений в версии 1 нет.

Для MapLibre экспортируется приблизительное положение около `[36.60, 55.10]` в порядке **долгота, широта**. Преобразование:

```text
R = 6371008.8 м
lon = lon0 + degrees(x / (R * cos(radians(lat0))))
lat = lat0 + degrees(y / R)
```

Это малая локальная аппроксимация для отображения, не официальная проекция. GeoJSON соответствует порядку координат RFC 7946. В экспортных слоях координаты округлены до 8 знаков; обратное преобразование этих значений не следует использовать как источник точной геометрии.

## Общие правила идентификаторов и версий

- `id` уникален во всём наборе и содержит строчные латинские буквы, цифры, `_` и `-`. Связи задаются ID, а не порядковым номером в массиве и не названием.
- `b00` означает квартал строки 0, столбца 0. Строки идут с юга на север, столбцы — с запада на восток. Суффиксы `sw`, `se`, `nw`, `ne` — стороны света; `c` — центр, `cw` и `ce` — узлы дворового пути западнее и восточнее центра.
- Подписи «Жилой дом 01» декоративные. Для сохранённых сценариев и пользовательских данных использовать только `id`.
- Генерация населения использует отдельный seed из SHA-256 основного seed и ID здания. Добавление другого здания не меняет население существующих зданий с теми же ID и этажностью.
- Воспроизводимость гарантируется для одинаковой версии генератора и Python. Если меняются правила генерации, увеличивать `datasetVersion`; изменение смысла или структуры полей требует изменения `schemaVersion`.
- Экспортируемый пользовательский сценарий в будущем должен хранить ID района, версию данных и SHA-256 исходного `district.json`. Сценарий другой версии нельзя незаметно применять к новой базе.

## Сущности

| Массив | Ключевые поля | Назначение |
|---|---|---|
| `roads` | `polygon`, `axis`, `centerM`, `widthM` | Проезжие части как непроходимые геометрические барьеры |
| `blocks` | `polygon`, `landUse` | Кварталы и общая организация района |
| `parcels` | `polygon`, `kind`, `areaM2`, `fence` | Землепользование, границы парков и школьных участков |
| `buildings` | `polygon`, `floors`, `heightM`, `entranceNodeIds`, `population` | Застройка и жители |
| `nodes` | `xy`, `kind`, `active`, `blockId` | Точки связности графа, входы, ворота |
| `edges` | `from`, `to`, `geometry`, `lengthM`, `active`, `bidirectional` | Доступные и заранее подготовленные связи |
| `destinations` | `kind`, `accessNodeIds`, `active`, ссылки на здание/участок/место остановки | Объекты, до которых считается доступность |
| `stopBays` | `nodeId`, `roadId`, `side`, `routeIds` | Допустимые места остановок на правильной стороне улицы |
| `transitServices` | `id`, `routeGeometryModelled` | Реестр условной автобусной линии для совместимости остановок |
| `profiles` | Скорость, допустимость ступеней, уклона, ширины и поверхности | Условия передвижения |
| `projects` | Стоимость, зависимости, конфликты, операции | Варианты изменений района |
| `scenarios` | `projectIds`, `budgetRub`, `operationalOverrides` | Сохранённые проекты и эксплуатационные события |

Семантика `active` зависит от сущности. Для узла и ребра это доступность в текущем состоянии графа; для объекта притяжения — существование/открытость в модели. Для участка это наличие участка в рассматриваемом районе. Резерв под будущий сквер уже существует как активный участок `vacant`, а вход, связь с ним и объект `park` до проекта неактивны.

Здания версии 1 нельзя сносить или переселять. Все будущие скверы расположены на свободных участках. Создание сквера меняет вид использования участка на `public_park`, активирует его вход, путь и объект притяжения; жители при этом сохраняются.

## Геометрия и граф

Отрисованная линия не создаёт связь сама по себе. Связь существует только через общие `from` / `to`. Все пересечения наземных дорожек должны быть разбиты общим узлом. Пересечения без узла, дубли узлов в одной точке и перекрывающиеся рёбра запрещены. Будущие мосты и тоннели потребуют уровня высоты и новых правил.

Ребро содержит полилинию `geometry`, начинающуюся в координатах `from` и заканчивающуюся в `to`. `lengthM` — сумма евклидовых длин её отрезков с округлением до 6 знаков. Отрицательные и нулевые длины недопустимы. Исходные рёбра двунаправленные; эталонный алгоритм поддерживает `bidirectional: false`.

Проезжую часть можно пересекать только ребром `kind: crossing`. Такое ребро пересекает ровно одну дорогу, указанную в `crossing.roadId`. На каждом переходе заданы тип регулирования, условное ожидание, понижения бордюров и тактильное покрытие. Ожидание учитывается при каждом прохождении ребра и является фиксированным ожидаемым временем, а не моделью фаз светофора.

Тактильное покрытие — описательный атрибут; профиль для слабовидящих в версии 1 не моделируется. Нельзя выводить из него сертифицированную безопасность маршрута.

Пешеходные пути не проходят через внутренность здания. Вход в здание лежит на его фасаде. У школ есть ограждённые участки и явные ворота; путь к школе проходит через ворота. Школьный участок не даёт сквозного общественного прохода. В расчётах школа считается доступной как пункт назначения, без проверки права прохода конкретного жителя.

Парк — участок и объект с одним или несколькими входами. Для доступности выбирается ближайший достижимый вход. Пересечение границы парка допускается только в объявленных входах. Внутренние дорожки могут быть транзитными, если это отражено в графе.

Отключённая связь остаётся в наборе как известный коридор. Не следует удалять её запись при закрытии: ID нужен проектам, отмене и сохранённым сценариям. Новый произвольный коридор требует создания узлов, разбиения пересечений, проверки барьеров и явного определения стоимости; такие операции пока не входят в контракт проектов.

## Население

`population` существует только у жилых зданий. Публичные здания имеют `population: null`; учащиеся, работники и посетители не дублируются в числе постоянных жителей.

Поля:

- `total` — число жителей дома.
- `ageGroups` — взаимно исключающие группы до 18 лет, 18–64 и от 65 лет; сумма равна `total`.
- `mobilityNeedsResidents` — условная часть населения с потребностями мобильности. Эта группа **пересекается** с возрастными и не прибавляется к ним.
- `apartments` — общее число квартир; `occupiedApartments` — заселённые квартиры.
- `households` — число домохозяйств. В версии 1 одно домохозяйство занимает одну заселённую квартиру.
- `householdSizeCounts` — число домохозяйств размером от 1 до 5 человек. Сумма количеств равна `households`, взвешенная сумма — `total`.

Не генерируются имена, адреса регистрации, возраст отдельных людей и чувствительные индивидуальные профили. Для контроля правдоподобия проверяется средняя площадь квартиры по условной полезной доле площади здания 0.72; это техническое допущение генератора, не норматив строительства.

Все жители дома начинают путь с его входов. Если входов несколько, для всего дома выбирается лучший достижимый: расселение по подъездам пока не задано. Для более точной модели население нужно распределить по входам отдельными записями.

## Профили и время движения

| Профиль | Скорость | Ступени | Максимальный модуль уклона | Минимальная ширина | Понижения бордюра |
|---|---:|---|---:|---:|---|
| `walk` | 1.25 м/с | Допустимы | 0.20 | 0.8 м | Не обязательны |
| `step_free` | 0.85 м/с | Исключены | 0.05 | 1.5 м | Обязательны на переходах |
| `slow_walk` | 0.80 м/с | Допустимы | 0.12 | 0.9 м | Не обязательны |

Уклон хранится как отношение подъёма к горизонтальной длине: `0.05` = 5%. Это не угол в градусах. В текущей модели проверяется абсолютное значение; разная скорость вверх и вниз не рассчитывается. При равенстве порогу уклона или ширины ребро допустимо.

Покрытия `asphalt`, `paving`, `compacted_gravel` имеют коэффициент скорости для каждого профиля. Коэффициент меньше единицы замедляет движение. Профиль без ступеней допускает уплотнённый гравий с сильным замедлением; это условное правило, которое можно изменить в профиле.

```text
timeSeconds = lengthM / (speedMps × surfaceSpeedFactor) + crossingWaitSeconds
```

Недопустимое ребро исключается из графа полностью, а не получает очень большое время. Оба узла ребра и само ребро должны быть активны. Все веса положительные. Расчёт — многоточечный алгоритм Дейкстры по обратному графу от входов объектов. Это даёт время **от дома к объекту**, включая будущие однонаправленные связи.

Текущий критерий маршрута — минимальное время с учётом ожидания. Самый быстрый путь может отличаться от самого короткого по длине. Для отображения длины найденного пути складываются `lengthM` его рёбер; для отдельной метрики кратчайшего расстояния потребуется запуск с весом `lengthM`.

Равные пути выбираются детерминированно по порядку ID. При переносе на другой язык важнее равенство времени, допустимость пути и конечной точки, чем совпадение одного из нескольких равноценных маршрутов.

## Метрики

Пороги задаются в секундах и являются настраиваемыми допущениями, не нормативами:

| Объект | Порог |
|---|---:|
| Остановка | 420 с, 7 минут |
| Парк или сквер | 600 с, 10 минут |
| Школа | 900 с, 15 минут |
| Поликлиника | 900 с, 15 минут |
| Продуктовый магазин | 600 с, 10 минут |

Районный центр хранится как дополнительный общественный объект, но не включён в пять основных метрик. Добавлять его в показатели нужно явно, согласовав порог и код расчёта.

Для каждого дома выбирается минимальное время от любого его входа до любого входа активного объекта нужного типа. Равенство временному порогу считается доступностью. Решение о пороге принимается **до округления** времени; в отчёте время округлено до 0.001 с.

Для каждого типа объекта сохраняются:

- `reachableResidents` и `unreachableResidents`; сумма равна всему населению.
- `withinThresholdResidents` — жители домов, попавших в порог.
- `coveragePercent = 100 × withinThresholdResidents / allResidents`.
- `meanSecondsReachableOnly` — сумма `население дома × время` для достижимых домов, делённая на число достижимых жителей.

При недостижимости в записи дома `travelSeconds: null`, `reachable: false`, `withinThreshold: false`. Если ни один житель не достигает объектов данного типа, среднее равно `null`, покрытие — 0. В JSON не используются `Infinity`, `NaN` и большие фиктивные значения.

**Среднее по достижимым необходимо показывать вместе с числом недостижимых.** Изоляция удалённого дома может улучшить такое среднее, ухудшив реальную доступность района. Нельзя ранжировать проекты только по этому среднему, игнорируя охват. Для будущего подборщика разумна явная цель: сначала максимизировать охват, затем минимизировать время при одинаковом охвате; конкретное правило выбора нужно зафиксировать в настройках.

Школьная доступность по умолчанию считается для всех жителей, чтобы метрики были сопоставимы. `ageGroups.under18` позволяет добавить отдельную метрику для детей; это ещё не распределение по школам и не проверка свободных мест. `capacity` хранится с запасом, но не ограничивает доступность.

Площадь публичных парков — сумма уникальных активных парковых участков, включая дорожки. Один парк с четырьмя входами не считается четырьмя парками. Это не площадь кроны деревьев.

В сравнении для каждого вида объекта жители относятся к одной из групп: путь улучшился, ухудшился, не изменился. Переход от недостижимости к достижимости — улучшение, обратный — ухудшение, обе недостижимости — отсутствие изменения. Допуск сравнения — 0.01 с после представления времени с точностью 0.001 с. Разность процентов покрытия хранится в **процентных пунктах**.

Одни и те же жители учитываются в нескольких типах объектов и профилях. Нельзя суммировать такие значения как число уникальных людей. `step_free` оценивает гипотетическую доступность для всех жителей при этом профиле, а не только `mobilityNeedsResidents`.

## Проекты и сценарии

Проект содержит:

- целочисленные `capexRub` и `annualOpexRub`; единицы — рубли, не копейки;
- `priceYear: 2026`, `isSynthetic: true`;
- зависимости `requires`, явные несовместимости `excludes`, необязательную группу `exclusiveGroup`;
- последовательность типизированных операций.

Стоимость — учебное допущение. Ежегодные расходы генерируются как 3.5% капитальных, округлённые до рубля; их нельзя выдавать за финансовую оценку. `budgetRub` ограничивает только капитальные расходы. Ежегодные расходы показываются отдельно; отрицательные стоимости и доходы не используются.

| Операция | Параметры помимо `op` и `targetId` | Значение |
|---|---|---|
| `set_node_active` | `value` | Включить/выключить узел |
| `set_edge_active` | `value` | Открыть/закрыть подготовленный путь |
| `set_destination_active` | `value` | Активировать/деактивировать объект |
| `set_parcel_use` | `kind: public_park` | Превратить резервный участок в парк |
| `relocate_destination` | `nodeId`, `stopBayId` | Переместить остановку в допустимое место |
| `upgrade_edge` | `changes` | Изменить покрытие, ступени, уклон, ширину или понижение бордюра |

`changes` не должен быть пустым. Он разрешает только `surface`, `stairs`, `slope`, `widthM`, `kerbRamps`. Это обычные поля, не произвольный код и не JSONPath.

Выбор проектов хранится без повторов. Зависимости должны присутствовать в списке **раньше** зависящего проекта. Две альтернативы одной `exclusiveGroup` нельзя выбрать одновременно. Например, `p_stop_north` и `p_stop_south` перемещают одну остановку в разные места. `p_park_paving` требует `p_park_b10`.

Остановку можно переносить только между допустимыми `stopBays` той же улицы, стороны и совместимой условной линии. Время поездки, интервалы, направление автобуса и посадка не моделируются. `stepFreeBoardingAssumed` — допущение, не результат проверки конструкции платформы.

Применение сценария:

1. Проверить версию базы, ID, повторы, зависимости, конфликты и бюджет.
2. Создать копию исходного района.
3. Применить операции выбранных проектов по порядку.
4. Применить `operationalOverrides` — события вроде временного закрытия перехода.
5. Проверить целостность итогового состояния и рассчитать показатели.

Сброс — новая копия исходного состояния, без обратных арифметических патчей. Так ошибка накопления не меняет базу. Эксплуатационные события не имеют капитальной стоимости; они не предназначены для бесплатного строительства. В пользовательском интерфейсе такие события нужно отделить от выбора проектов и ограничить разрешёнными типами.

Эталонный модуль `district_model.py` рассчитан на доверенные сценарии этого набора. Он не является API для приёма произвольных неподтверждённых пользовательских команд. Будущему приложению нужны проверка схемы входного сценария, ограничения допустимых событий и проверка итогового состояния.

Все проекты не обязаны улучшать каждую метрику. Открытый проход может дать нулевой эффект для текущих объектов и стать полезным после другого изменения. Перенос остановки намеренно даёт выигравших и проигравших. Ни один сохранённый сценарий не объявлен оптимальным.

## Проверка качества и контрольные результаты

Валидатор проверяет структуру по поставляемой схеме, глобальные ID и ссылки, единицы и диапазоны, замыкание/ориентацию/самопересечения полигонов, площади, размещение зданий в участках и участков в кварталах, население, геометрию и длины рёбер, отсутствие скрытых пересечений, дорожные и школьные барьеры, входы парков, стороны остановок, исходную связность и применимость каждого проекта с зависимостями и каждого сохранённого сценария.

Полная проверка геометрии рассчитана на маленький учебный район; часть проверок попарная и не предназначена для графа всего города. При масштабировании понадобится пространственный индекс.

Тесты отдельно сверяют Дейкстру с независимым алгоритмом Беллмана—Форда, проверяют направленность, ожидание, ограничения профилей, взвешивание населением, точное включение порога, недостижимость, конфликты/бюджет/порядок проектов, неизменность исходной базы, пользу пандуса, выигравших/проигравших от переноса остановки, GeoJSON и хеши файлов. Намеренно повреждённые данные должны отклоняться.

Рекомендуемый допуск переноса расчётов на TypeScript: 0.002 с для времён из отчёта и 0.002 процентного пункта для процентов; целочисленные количества жителей и рубли должны совпадать точно. У пороговых значений использовать неокруглённое время и правило включения границы. Python и JavaScript могут различаться в округлении точных половин; сравнивать с допуском.

## Что расширять следующими версиями

Подготовлены опорные поля для новых объектов, порогов, профилей, публичных участков и проектов. Отдельного изменения модели потребуют: население по входам, обслуживание по вместимости, реальные перепады высот, расписание, ночные закрытия, динамические светофоры, веломаршрутизация, снос и переселение, произвольная геометрия редактора, транспортная модель и строительная смета.

Рабочее ядро TypeScript и точный оптимизатор реализованы в `src/core/`; описание API, ограничений поиска и интеграции — в `docs/ENGINE.md`. Пользовательский редактор и сервер пока не созданы.
